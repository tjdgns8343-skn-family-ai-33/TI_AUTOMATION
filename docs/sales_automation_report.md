# 영업 업무 자동화 보고서 (쉬운 버전)

작성일: 2026-10-12 · 읽는 사람: 이 프로젝트를 만든 본인 (기술 영업 지원 준비용)
자세한 수치와 근거: [sales_measurement_2026-10-12.md](sales_measurement_2026-10-12.md) · 구조: [architecture.md](architecture.md) · MCP 사용법: [mcp_workflow.md](mcp_workflow.md)

## 1. 한 줄 요약

기존에 만든 "기술 문의 처리 프로그램"에 **영업 쪽 일**을 붙였습니다.
고객이 샘플·견적을 요청하거나 "이런 조건에 맞는 부품을 추천해 달라"고 하면 → 프로그램이 정리하고 → **사람이 승인할지 말지 결정**하고 → 승인되면 메일 초안·보고서·요약이 **저절로 만들어집니다.**
이 전체를 MCP(프로그램끼리 연결하는 표준 방식)로 묶어서, Claude Desktop 같은 도구에서 단계별로 부를 수 있게 했습니다.

가장 중요한 원칙 하나: **가격·납기·재고는 이 프로그램이 절대 말하지 않습니다.** 그 데이터가 없기 때문에, 아는 척하지 않고 "영업 시스템에서 확인 후 담당자가 회신"으로 넘깁니다.

## 2. 처음 요청한 4가지가 어떻게 됐나

| 요청 | 한 일 | 상태 |
| --- | --- | --- |
| 1. 컴플레인·요구사항이 오면 분류·분석 (RAG 또는 fine tuning) | 문의를 6가지로 분류(기술, 품질 클레임, **견적·샘플**, **설계 상담**, 배송, 기타). 부품 정보는 데이터시트에서 옮겨 적은 "부품 카드"와 비교 | 됨. 단, fine tuning(모델 재학습)은 **안 했습니다** |
| 2. 해결방안 제시 | 견적·샘플: 빠진 정보를 찾아 되묻기. 설계 상담: 조건에 맞는 부품을 계산으로 비교해 후보와 탈락 이유 제시 | 됨 (전원 부품 LDO·벅만) |
| 3. 사람이 승인할지 말지 | 초안에서 멈추고 사람이 승인 / 수정 요청 / 반려. 승인 전에는 문서가 만들어지지 않음 | 됨 |
| 4. 승인되면 자동 문서화 | 고객 메일 초안, 내부 보고서, 티켓 요약을 파일로 저장 (발송은 안 함). 승인된 내용에 없는 숫자·약속이 들어가면 만들지 않음 | 됨 |
| (묶기) MCP | 서버 3개: `fae_workflow`(접수→승인→문서화), `sales`(분류·점검·추천), `docs`(문서 조회·검사) | 됨 (Claude Desktop 화면 연결은 **아직 직접 해보지 않음**) |

## 3. 어떻게 움직이나 (그림)

```text
고객 문의
   │
   ▼
[접수·분류]  ── 기술 문의 ──▶ (기존) 원인 분석·계산·시뮬레이션·검수
   │
   ├─ 견적·샘플 요청 ──▶ [요청 점검]  빠진 정보(수량·용도·시점…)를 찾는다. 가격·납기는 말하지 않는다
   │
   └─ 설계 상담 ───────▶ [부품 추천]  입력·출력·전류를 부품 카드와 숫자로 비교한다
                              │
                              ▼
                    [답변 초안 작성]  (모델이 쓰고, 코드가 검사한다. 틀리면 코드가 만든 답변으로 바꾼다)
                              │
                              ▼
                    [사람 승인]  승인 / 수정 요청 / 반려
                              │ (승인일 때만)
                              ▼
                    [자동 문서화]  메일 초안 · 내부 보고서 · 티켓 요약  (발송은 사람이)
```

## 4. 이번에 한 일 순서대로

1. **승인 뒤 자동 문서화** — 승인해야만 문서가 생깁니다. 문서에 새 숫자·약속·가격 같은 말이 끼어들면 코드가 막습니다.
2. **영업 문의 두 종류 추가** — 견적·샘플 요청, 설계 상담. 평가용 가상 문의 9건(S-1~S-9)을 만들고 정답을 손으로 계산해 둠.
3. **MCP 서버로 묶기** — 외부 도구가 "접수 → 초안 확인 → 승인 → 문서 열람"을 단계별로 호출.
4. **LLM(OpenAI 모델)으로 측정** — S 9건. 결과가 기대보다 좋지 않아서 5번으로.
5. **답변 검사 추가** — 모델이 쓴 답변을 코드가 확인. 빼먹거나 어기면 코드가 만든 답변으로 대체.
6. **새 문의 9건(V-1~V-9)으로 다시 측정** — 검사 규칙을 만들 때 보지 않은 문의. 코드의 빈틈 7곳을 먼저 발견해 고치고, 그 뒤 측정.

## 5. 숫자로 본 결과

용어: **LLM 모드** = 실제 OpenAI 모델을 쓰는 모드(돈이 듦). **mock 모드** = 모델 없이 규칙만 쓰는 모드(공짜, 테스트용). **기준선** = 부품 정보와 계산 없이 모델 혼자 답하게 한 것(비교용).
채점은 문의마다 미리 정한 4~5개 항목(rubric)을 ✓(충족) △(일부) ✗(못함)로 센 것입니다. 분류 항목은 제외했습니다.

| 측정 | 문의 | 쓴 토큰 | 충족 / 일부 / 못함 |
| --- | --- | --- | --- |
| S 9건, 모델이 쓴 답변 그대로 | 34항목 | 65,578 | **19 / 6 / 9** |
| S 9건, 기준선(모델 혼자) | 34항목 | 6,392 | 11 / 10 / 13 |
| V 9건, 답변 검사 포함 | 33항목 | 66,313 | **29 / 4 / 0** |

토큰: 영업 작업에 약 13.8만, 프로젝트 전체 누적 약 161만. 진행 전에 매번 예상치를 말씀드리고 승인받았습니다.

### 이 숫자를 읽는 법 (중요)

- **S에서 모델은 기준선보다 낫지만 구멍이 컸습니다.** 코드가 계산한 부품 이름과 숫자(0.22 W, 5.85 W 등)는 정확히 전달했습니다. 하지만 **탈락한 부품을 답변에서 빼먹었고**, 특히 "조건에 맞는 부품이 하나도 없다"는 경우(S-6)에는 계산 결과를 무시하고 엉뚱한 질문을 했습니다. 불필요한 질문(회사명·배송지)도 붙였고, 답변에 `[source]` 같은 글자가 새어 나온 적도 있습니다.
- **V의 29/4/0은 모델이 잘해서가 아닙니다.** 9건 중 6건은 검사에 걸려 **코드가 만든 답변**으로 바뀌었습니다. 코드 답변은 항상 후보·탈락 이유·가정·범위를 싣도록 만들어서 그 항목이 맞는 건 당연합니다. "모델 + 코드 안전망"의 점수이지 모델 단독 점수가 아닙니다.
- **검사가 잘못 잡은 것도 있었습니다.** 번호 목록 "3. 원하시는…"을 가격 "3. 원"으로 읽은 오류(V-4). 고쳤지만 다시 측정하지는 않았습니다.

## 6. 이번에 알게 된 것 (쉬운 말로)

1. **모델에게 "계산 결과를 빠짐없이 전해라"고 부탁만 하면 가끔 빼먹습니다.** 확실히 하려면 코드로 확인해야 합니다. (기술 문의 때도 같은 결론이었습니다.)
2. **"모른다"를 구조로 보장하면 안전합니다.** 가격·납기 데이터가 아예 없으니 말할 수 없고, 문서 검사가 약속 표현을 막습니다. 말로 부탁하는 것보다 믿을 수 있습니다.
3. **문의를 새로 만들면 코드의 빈틈이 바로 드러납니다.** V를 만들자마자 7곳이 정답과 달랐습니다("사용처는", "연말까지", "USB 5V에서 3.3V", 부품이 지원하는 출력 전압 범위를 확인하지 않던 것 등).
4. **정답은 코드를 보기 전에 정해야 정직합니다.** 이번에도 정답을 먼저 손으로 계산해 두고 코드와 비교했습니다. 틀린 쪽이 코드일 때 정답을 코드에 맞추지 않았습니다.
5. **승인 단계는 "프로그램 구조"로 강제해야 합니다.** 승인 전에는 문서를 만드는 길 자체가 없습니다.

## 7. 솔직한 한계

- **사례가 적습니다.** S 9건, V 9건, 각각 한 번씩만 돌렸습니다. 정답을 만든 사람과 채점한 사람이 같습니다(저).
- **V는 이제 "처음 보는 문의"가 아닙니다.** 접수 규칙을 V를 보고 고쳤습니다. 진짜로 보지 않은 문의로 다시 재려면 새로 만들어야 합니다.
- **추천은 부품 카드가 있는 6종 안에서만 합니다.** TI 전체 제품을 검색하는 것이 아닙니다. 연산증폭기·충전기·통신 부품 추천은 "지원 안 함, 담당자 검토"로 넘깁니다.
- **가격·납기·재고 데이터가 없습니다.** 견적은 "빠진 정보를 되묻고 담당자에게 넘기는" 데까지입니다.
- **검사로 바뀐 모델 답변 원본을 저장하지 않았습니다.** 모델이 원래 얼마나 틀렸는지 지금은 확인할 수 없습니다.
- **검사가 못 보는 것:** 이미 고객이 준 정보를 다시 묻는 경우(V-7, V-8에서 확인), 문장이 어색한지, 고객의 할인 요구에 대한 한마디(V-2 답변이 그 요구를 언급하지 않음).
- **MCP는 호출자가 사람인지 모델인지 구별하지 못합니다.** 사용하는 도구(Claude Desktop 등)가 호출마다 사람에게 확인을 받도록 둬야 승인 단계가 의미가 있습니다. 서버를 끄면 승인 대기 중이던 건은 사라집니다.
- **Claude Desktop 화면에서 직접 연결해 본 적은 없습니다.** 서버를 실제로 띄워 호출하는 테스트까지만 했습니다.

## 8. 이 프로젝트로 말할 수 있는 것 / 없는 것

**말할 수 있는 것 (근거가 있음)**
- 영업 문의(견적·샘플, 설계 상담)를 접수 → 분류 → 점검·추천 → 사람 승인 → 문서화까지 자동화한 동작하는 프로그램과, 이를 MCP로 호출할 수 있는 서버 3개.
- 모델이 틀릴 수 있는 곳을 측정으로 찾고, 코드 검사로 막는 과정을 반복했다는 것. (S에서 못함 9건 → V에서 0건, 단 위 한계 전제)
- 가격·납기처럼 데이터가 없는 것은 말하지 않게 구조로 막았고, 사람 승인 전에는 문서가 만들어지지 않는다는 것.
- 테스트 316개 통과(+1 건너뜀), 백엔드 15개 통과.

**말하면 안 되는 것 (근거가 없음)**
- "정확도 몇 %"처럼 일반화된 성능. 표본이 작고 채점자가 저 자신입니다.
- "실제 영업 시스템에 연결됐다" / "TI 전 제품을 추천한다" / "fine tuning을 했다".
- "Claude Desktop에서 확인했다" (아직 안 함).

## 부록: 용어 사전

- **RAG**: 모델이 답하기 전에 관련 문서를 먼저 찾아 보여 주는 방식. 이 프로젝트의 기술 문의는 데이터시트 문장을 검색해 근거로 씁니다. 영업 쪽은 정리된 "부품 카드" 값을 직접 비교합니다.
- **fine tuning**: 모델 자체를 추가로 학습시키는 것. 이 프로젝트에서는 하지 않았습니다.
- **MCP**: 프로그램(도구)을 AI 도구가 부를 수 있게 하는 공통 규격. 여기서는 "접수", "승인", "문서 열람" 같은 기능을 서버로 열어 둔 것.
- **human in the loop**: 중요한 결정(승인)을 사람이 하는 구조.
- **부품 카드**: 데이터시트의 한계값·특성을 사람이 옮겨 적은 파일. 출처(쪽 번호)가 적혀 있습니다.
- **템플릿 답변**: 모델 없이 코드가 정해진 틀에 결과를 채워 만든 답변.
- **rubric**: 채점 항목 목록. 측정 전에 정합니다.
