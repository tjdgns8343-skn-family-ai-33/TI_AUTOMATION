# 가능성 검증 보고서

작성일: 2026-09-29, 2026-09-30 갱신 · 대상: 실제 TI 부품 3종 (TPS7A20, LM2596, LMV321A) · 가상 고객 문의 32건
(교과서 수준 20건 + 구체적인 문의 12건)

## 1. 한 줄 결론

**조건부로 가능하다. 다만 가치는 "정확도 향상"이 아니라 "근거와 계산 숫자가 붙은 초안을 사람이 승인하는 것"이다.**
실제 데이터시트를 근거로 문의를 접수하고 원인 후보와 계산 검증, 답변 초안, 사람 승인까지 끝까지 동작한다.
그러나 도구 없는 LLM과 비교하면 원인 적중률은 쉬운 문의에서 같고(15/18 대 15/18), 구체적인 문의에서는 오히려 낮았다(1순위 7/10 대 9/10).
파이프라인이 앞선 것은 답에 나오는 정답 숫자(11/18 대 4/18)와 잘못된 고객 전제 정정이었고, 비용은 약 24배다.

| 질문 | 답 | 근거 |
| --- | --- | --- |
| 실제 부품·데이터시트로 끝까지 돌아가는가 | **예** | 3종 32건 모두 오류 없이 완료. 인용한 출처가 실제 존재 (부적절 인용 2건/239건) |
| 도구 없는 LLM보다 원인을 더 잘 맞히는가 | **아니오 (이번 실험에서는)** | 쉬운 문의 1순위 15/18 대 15/18, 구체적 문의 1순위 7/10 대 9/10. 표본이 작고 채점자가 작성자 |
| 근거·계산 숫자를 답에 실어 주는가 | **예** | 구체적 문의에서 정답 숫자가 답에 나온 비율 11/18 대 4/18. 고객의 잘못된 전제("500 mA까지 된다")를 부품 카드로 정정 |
| 계산·시뮬레이션 검증이 믿을 만한가 | **아니오 (현재는)** | 테스트 47개 중 55%가 값 대조, 5개는 값이 경계와 같아 무조건 통과. 검수가 이를 못 걸러냄 |
| 비용·시간이 감당 가능한가 | **아니오 (현재는)** | 구체적 문의 건당 17,860 토큰 (기준선의 23.8배), 26초 (5.4배). 검수 미통과로 끝난 4건이 토큰의 43% 사용 |

- 데이터시트는 사용자가 직접 내려받았다 (TI 약관상 자동 수집 금지). 3개 PDF에서 검색용 조각 338개를 만들었다.
- 부품 카드 3장(`data/parts/*.yaml`)은 데이터시트의 표에서 값을 직접 읽어 옮겼고(기호가 깨지는 표는 페이지를 이미지로 확인), 값마다 페이지를 주석으로 적었다.

### 2.2 고객 문의 20건 (`data/eval/eval_real_parts.jsonl`)

부품당 기술 문의 6건, 품질 클레임 1건, 배송 문의 1건 (마지막 둘은 분류 확인용).
각 문의에는 정답 원인(`ground_truth`), 데이터시트 근거 위치, 자동 판정용 키워드를 함께 적었다.
증상은 과열, 발진, 리플, 출력 이상, 기동 실패를 골랐고, 정격 초과 3건, "정상 동작인데 불량으로 착각" 1건, 극성 오해 1건을 넣었다.

### 2.3 비교한 세 가지 방식

| 방식 | 하는 일 | 모델 |
| --- | --- | --- |
| **mock** | 규칙 기반. LLM 없음 | 없음 |
| **파이프라인 (llm)** | 접수 → 근거 검색 → 원인 분석 → 계산·시뮬레이션 → 검수(최대 2회 재분석) → 답변 | OpenAI gpt-5.4-mini |
| **기준선 (baseline)** | 같은 모델에 문의만 주고 한 번 호출. 검색·도구·검수 없음 | 같은 모델 |

파이프라인은 1회차 20건, 반복 2회(각 9건에서 중단)를 돌렸다. 기준선은 20건씩 2회 돌렸다.
반복을 9건에서 멈춘 것은 토큰 사용량(약 53만 토큰) 때문이며, 남은 반복은 필요하면 재개할 수 있다.

### 2.4 채점 방법과 한계

- **자동 판정**: 원인 후보 3개의 제목·설명에 정답 키워드가 있는지. 빠르지만 부정확하다.
- **수동 채점** (1회차): 정답 원인이 후보에 의미상 들어 있는지 1순위와 Top-3로 직접 읽고 채점했다.
- **한계**: 문의 작성자, 시스템 조정자, 채점자가 모두 같은 사람이다. 실제 고객 문의가 아니고 교과서 수준이다. 표본은 18건이다.

### 3.3 검증 테스트의 질 (가장 중요한 발견)

반복 2회 9건씩의 테스트 47개(참고용 계산 제외)를 분류했다.

| 종류 | 개수 | 비율 | 의미 |
| --- | --- | --- | --- |
| 공식 계산 (접합 온도, 리플, 출력 전압 등) | 19 | 40% | 입력에 따라 결과가 달라지고 실패할 수 있는 진짜 검증 |
| 회로 시뮬레이션 (ngspice) | 2 | 4% | 같음. 다만 적용이 맞는지 별도 확인 필요 |
| 값 대조 (`check_value`) | 26 | 55% | 데이터시트 한계와 숫자를 비교. 정격 초과 확인에는 유효 |
| 그중 값이 합격 범위 경계와 같아 **무조건 통과** | 5 | 11% (값 대조의 19%) | 아무것도 증명하지 못함 |

무조건 통과하는 예:

- T-05 reproduce: 값 0.0, 합격 범위 0.0~0.1 ("EN 플로팅 재현")
- T-06 reproduce: 값 0.3, 합격 범위 0.3~0.3
- L-03 reproduce: 값 4.7 µH, 최소 4.7 µH

1회차에서 눈으로 확인한 잘못된 도구 사용:

- A-01(연산증폭기 용량성 부하)에 LC 필터 부하 스텝 시뮬레이션을 돌려 `undershoot_pct=0`을 "안정화 확인"으로 씀
- T-06(드롭아웃)을 접합 온도 계산으로 "재현"

**검수가 이것들을 하나도 걸러내지 못했다.** 검수는 "테스트 결과가 기대 범위 안인가"만 보고, 기대 범위가 의미 있는지는 보지 않는다.
그래서 "검수 18/18 통과"는 정확도 증거가 아니다.

검증이 진짜 신호를 준 경우도 있다. r2의 L-02와 r3의 L-03은 제안한 해결책의 계산 결과가 목표에 못 미쳐(예: 리플 61 mV > 목표 50 mV) 3회 재분석 후에도 미통과로 끝났다.
계산 도구가 붙은 사례에서는 검증 루프가 의도대로 동작한다.

### 3.4 근거 인용

- 원인 후보에 붙은 인용 196건(1회차 94, r2 53, r3 49) 중 존재하지 않는 출처는 1건 ("근거 목록"이라고만 적음).
- r2·r3는 모델이 받은 근거 안에서만 인용했다.
- **한계**: 출처가 실제로 존재하는지만 확인했다. 그 페이지가 주장을 뒷받침하는지는 확인하지 못했다.
- 첫 집계에서 "인용의 절반이 환각"으로 나왔는데, 대괄호 `[출처]`와 부품 카드 원문 표기 때문에 생긴 측정 오류였다. 정규화 후 위 수치가 됐다.

### 3.5 변동성, 시간, 비용

- 같은 9건의 재분석 횟수 합: 1회차 1, r2 7, r3 5. 건당 시간 14.5 / 20.6 / 19.6초.
- 자동 판정 Top-3는 9/9, 8/9, 9/9로 안정적이었다. 흔들리는 것은 정확도보다 **재분석 횟수(비용과 시간)**다.
- 20건 파이프라인 1회차: 입력 188,012 + 출력 41,995 = 230,007 토큰. 기준선 20건은 14,641 토큰.
- 금액은 계산하지 못했다 (모델 단가를 확인하지 못함). 사용량은 OpenAI 사용량 페이지에서 확인할 수 있다.

## 4. 구체적인 문의 12건 (2026-09-30)

§3의 문의는 교과서에 나오는 답이라 일반 LLM도 풀 수 있어서 두 방식의 차이가 거의 나지 않았다.
그래서 데이터시트 숫자를 계산하거나 고객의 틀린 전제를 바로잡아야 답이 나오는 문의 12건(부품당 4건, `data/eval/eval_hard_cases.jsonl`)을 새로 만들었다.
정답 숫자는 계산으로 검산했다. 유형은 다음과 같다.

- 잘못된 전제: H-T2 "500 mA까지 된다"(실제 300 mA), H-L3 "60 V까지 된다"(실제 동작 40 V, 절대 최대 45 V)
- 정상인데 불량 의심: H-T3 출력 3.34 V (허용오차 ±1.5 %면 정상)
- 정보 부족: H-T4 "너무 뜨거워요", H-A3 "발진하는 것 같아요" (되물어야 정답)
- 부품 혼동: H-A4 (LMV321A는 1채널, 2채널은 LMV358A)
- 측정값과 계산 불일치: H-L1 (계산 리플 12.8 mV, 측정 120 mV, 프로브 GND 리드 10 cm)
- 미끼: H-A1 (슬루율이 아니라 GBW 100 kHz), H-T1 (열 차단 반복을 "불량"으로 의심)
- 그 밖: H-L2 (4 A, 정격 3 A 초과와 전류 제한), H-L4 (분압 11.32 V와 허용오차), H-A2 (오프셋 × 이득 500)

원인은 수동으로 채점했다(정보 부족 2건 제외 10건). 추가로 "정답 숫자가 답에 나오는지"와 "되물었는지"를 자동으로 셌다.

### 4.3 발견

1. **강점은 숫자와 전제 정정이다.** 정답 숫자가 답에 나온 비율이 11/18 대 4/18이고, 기준선이 고객의 틀린 전제를 받아들인 H-T2를 파이프라인은 부품 카드로 바로잡았다.
2. **원인 적중은 오히려 낮다.** H-L2는 부품 카드에 `iout_max 3.0`이 있는데도 무시했고, H-A2는 어제의 A-02와 같은 패턴으로 1순위가 틀렸다.
3. **"타 버림" 문의가 품질 클레임 경로로 간다.** 이 경로는 부품 카드를 보지 않아 "정확한 풀네임을 확인해 달라"고만 답했다. 실제 원인은 고객의 사용 조건(48 V > 절대 최대 45 V)이다.
4. **새 검수는 재분석을 크게 늘렸다.** 재분석 합 19회(§3은 20건에서 3회). 검수 미통과로 끝난 4건(H-T2, H-L2, H-A1, H-A2)이 토큰의 43%(91,505)를 쓰고도 나아지지 않았다.
   원인은 verify 단계의 자기 참조(한계값을 그대로 검증값으로 씀)와 `test_error`(고객이 주지 않은 인덕턴스를 0으로 넣음)였다.
5. **검수가 여전히 못 잡는 것**: 측정 문제(H-L1)에 회로 시뮬레이션을 돌린 것, 정보가 없는데 예시 값으로 계산한 것(H-T4). 도구 종류는 맞지만 용도가 틀린 경우다.

한계: 이 12건도 문의 작성자와 채점자가 같다. 원인 채점 대상은 10건이라 결론이 아니라 경향이다.

### 4.4 이후 조치 (재측정 전)

- 검수의 자기 참조 지적을 **재현(reproduce) 테스트에만 적용**하고 해결 확인(verify)은 경고로 바꿨다. 저장된 결과로 보면 H-T2와 H-A1의 미통과 사유가 이것이었다.
- 프롬프트에 세 가지를 추가했다: 고객이 주지 않은 값을 0으로 넣지 않는다, 해결 후 값이 한계와 같아지면 여유를 둔다, 핵심 조건이 없는 문의는 예시 값으로 계산하지 않는다.
- **품질 클레임 경로에 정격 점검을 추가했다** (2026-09-30, 재분류 없이 결과만 답변·8D·내부 메모에 붙임). H-L3를 LLM으로 다시 돌린 결과(3,512 토큰):
  답변 첫 문단에서 "알려 주신 값 기준으로 입력 48 V는 절대 최대 정격 45 V와 권장 최대 40 V를 초과"를 짚고 반품 절차와 자료 요청은 유지했다 (정답 숫자 2/2).
  진짜 불량 사례 X-01은 정격 초과를 주장하지 않았다. 첫 시도에서는 출처가 내부 경로(`parts/LM2596.yaml`)로 찍히고 40 V가 빠져서, 데이터시트 이름을 인용하고 권장 최대를 함께 적도록 고쳤다.
  한계: 접수 단계의 조건 추출이 틀리면 잘못된 비교가 된다 (규칙 기반 접수는 "입력 4.5V에서 60V까지"에서 4.5 V를 읽음). 부품 카드가 있는 부품에서만 작동한다.
- **검수 완화와 프롬프트 수정의 효과는 아직 재측정하지 않았다.** 효과를 보려면 LLM을 다시 돌려야 한다(약 20만 토큰).

## 5. 이번 실험 밖의 발견

- 시스템 전반은 실제 라이브러리(LangGraph 1.2, MCP, ngspice, Streamlit)에서 동작함을 확인했다.
- 시뮬레이션 파형을 화면에 그리는 기능을 추가했다 (수정 전·후를 겹쳐 표시).
- LLM 모드가 처음에는 검수를 통과하지 못해서 프롬프트에 지표 이름, 합격 범위의 방향, 역산 방법을 알려 주도록 고쳤다.
  이 수정으로 샘플 1건이 통과했고, 이번 20건 실험은 그 수정 이후의 결과다.

## 6. 결론과 다음 단계

**증명된 것**: 기술적 실현성. 실제 데이터시트 → 부품 카드 → 근거 인용 → 계산 → 사람 승인의 전체 흐름이 32건에서 오류 없이 동작한다.
그리고 답에 근거와 계산 숫자가 붙고 고객의 틀린 전제를 바로잡는다는 점이 도구 없는 LLM과 다른 점이다.
**증명 안 된 것**: 정확도 우위(구체적 문의에서는 오히려 낮음), 검증의 신뢰성, 실제 고객 문의에서의 성능, 비용 대비 효과(약 24배).

우선순위 순서:

1. **검수 강화** (일부 완료)
   - 완료: 값이 경계와 같은 재현 테스트 거부(검증 단계는 경고), 부품 종류에 맞지 않는 도구 거부, 정격 판정을 수치 비교로 변경, 테스트 구성 표시
   - 남음: reproduce 대조군(정상 조건이면 실패해야 통과), 도구 용도 확인(측정 문제에 회로 시뮬레이션), 정보가 없을 때 예시 계산 금지를 코드로 강제
   - 성공 기준: 자기 참조 테스트 0건, 잘못된 도구 사용 0건, 재분석 건당 0.5회 이하
2. **품질 클레임 경로에서 정격 비교** (완료): "타 버림" 문의도 부품 카드의 정격과 먼저 비교해 답변·8D에 붙임 (H-L3 재확인). 남은 것은 조건 추출 오류 방지와 부품 카드 확대.
3. **권장 범위를 벗어난 값을 원인 후보에 반드시 포함**: 지금은 절대 최대 초과만 강제한다 (H-L2의 4 A는 권장 초과라 놓침).
4. **도구 추가**: LDO 드롭아웃 여유, 벅 인덕터 리플 전류와 전류 제한 마진, 연산증폭기(슬루율, 오프셋×이득, 동상 범위, 용량성 부하 안정성)
5. **평가 확대**: 팀원이 결과를 보지 않고 쓴 문의 30건 이상, 사람 2명 채점, 3회 반복.
   성공 기준(안): 구체적 문의에서 기준선과 같은 원인 적중률을 유지하면서 정답 숫자·전제 정정 비율이 높을 것
6. **비용 관리**: 토큰 사용량을 코드에서 기록, 접수·검수에 작은 모델, 재분석 상한 유지
7. **인용 검증**: 임베딩 검색 + 인용 문장이 근거 조각에 실제 있는지 자동 확인
