# FAE Agent 기획안

## 한 줄 정의

반도체 부품 회사의 **고객 기술 문의를 받아, 데이터시트 근거와 계산·시뮬레이션 결과가 붙은 답변 초안을 만들고, FAE가 승인하면 나가게 하는** 멀티에이전트 시스템.

## 1. 풀려는 문제

- 고객 기술 문의(과열, 발진, 리플, 출력 이상, 기동 실패, 통신 오류)는 대부분 부품 불량이 아니라 **회로 설계나 사용 조건** 문제다.
- 담당 FAE는 문의마다 데이터시트를 찾아 정격과 조건을 대조하고, 손계산이나 시뮬레이션으로 원인을 확인한 뒤 답을 쓴다. 같은 종류의 문의가 반복된다.
- 답변 초안이 "근거 페이지"와 "계산 과정"을 함께 들고 오면 FAE는 처음부터 조사하지 않고 **검토와 승인**에 시간을 쓸 수 있다.

## 2. 무엇을 만드나

| 단계 | 하는 일 | 사용하는 것 |
| --- | --- | --- |
| 접수·분류 | 문의를 기술 / 품질 클레임 / 배송·기타로 나누고 부품·증상·조건 추출 | LLM |
| 기술 조사 | 데이터시트, 앱노트, 사례 카드에서 근거 검색, 부품 카드 조회 | 검색(TF-IDF), 부품 카드 |
| 원인 분석 | 원인 가설 3개와 해결책, 테스트 계획 작성 | LLM |
| 테스트 | 고객 조건에서 증상이 재현되는지, 해결책이 목표를 만족하는지 계산·시뮬레이션 | 설계 공식, ngspice |
| 검수 | 근거, 테스트 결과, 정격 초과 누락을 확인하고 미흡하면 재분석 (최대 2회) | 규칙 |
| 답변 초안 | 근거를 인용한 고객 답변과 내부 메모 | LLM |
| 사람 승인 | FAE가 승인, 수정 요청, 반려 | 화면 (Streamlit) |

- 품질 클레임(불량·반품)은 CPR 필수 자료 체크리스트와 8D 초안까지, 배송·기타는 담당 부서로 넘기는 초안까지만 한다.
- **범위 밖**: 실물 불량 분석, 실제 고객 데이터 연동, TI 사이트 자동 수집, 암호화된 SPICE 모델.

## 3. 핵심 아이디어와 검증 상태

| 가설 | 내용 | 검증 결과 (2026-09-29~30, 부품 3종 · 문의 32건) |
| --- | --- | --- |
| H1 근거·숫자가 붙은 초안 | 실제 데이터시트 페이지를 인용하고 계산 숫자를 답에 싣는다 | **확인됨**. 인용 239건 중 없는 출처 2건. 구체적 문의에서 정답 숫자가 답에 나온 비율 11/18 대 4/18 (주장을 뒷받침하는지는 미확인) |
| H2 숫자로 재현·검증 | 계산·시뮬레이션으로 원인과 해결책을 확인한다 | **부분 확인**. 테스트의 40%가 실제 공식 계산이고, 55%는 값 대조, 11%는 무조건 통과. 검수가 이를 못 걸러냄 |
| H3 단순 LLM보다 원인을 잘 맞힌다 | 도구 없는 LLM보다 원인 적중률이 높다 | **아니오 (이번 실험)**. 쉬운 문의 1순위 15/18 대 15/18, 구체적 문의 7/10 대 9/10. 고객의 틀린 전제 정정에서만 앞섬 |
| H4 사람 승인 안전장치 | 승인 없이는 발송되지 않는다 | **확인됨**. 승인·수정 요청·반려 흐름이 실제 라이브러리에서 동작 |

**가치 제안을 이렇게 잡는다.** 정확도 향상이 아니라 "근거와 계산 숫자가 붙고 고객의 틀린 전제를 바로잡은 초안을 사람이 승인한다"는 것이다.
비용은 도구 없는 LLM의 약 24배라서, 이 가치가 비용을 정당화하는지가 다음 검증 질문이다.

자세한 수치와 방법은 [feasibility_report.md](feasibility_report.md).

## 4. 데이터 원칙

- TI 데이터시트·에라타·앱노트는 **사람이 직접 내려받는다** (자동 수집은 약관상 금지).
- E2E 포럼은 크롤링하지 않는다. 사람이 읽고 자기 말로 요약한 **사례 카드**와 원문 링크만 저장한다.
- 부품 카드는 데이터시트 표에서 직접 옮기고 값마다 페이지를 적는다.
- 고객 이름과 연락처는 넣지 않는다. 평가용 문의는 가상 고객명을 쓴다.
- 자세한 내용은 [data_policy.md](data_policy.md).

## 5. 성공 기준 (안)

| 항목 | 목표 | 현재 |
| --- | --- | --- |
| 원인 Top-3 적중 (팀원이 쓴 블라인드 문의 30건 이상, 사람 2명 채점) | 기준선과 같거나 높음, 정답 숫자·전제 정정 비율은 기준선보다 높음 | 쉬운 문의 17/18, 구체적 문의 8/10 (기준선 9/10). 작성자=채점자 |

| 재분석 횟수 | 건당 0.5회 이하 | 구체적 문의 1.58회 (규칙 추가 후 재측정 전) |
| 건당 비용·시간 | 기준선의 5배 이내 | 구체적 문의 토큰 23.8배, 시간 5.4배 |
| 승인 없이 발송되는 경우 | 0건 | 0건 (구조상 불가) |

## 6. 로드맵

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |
| 0. 뼈대 (완료) | 전체 흐름, 도구 4종, 화면, mock 모드, 실제 라이브러리 검증 | 20건 오류 없이 완료 |
| 1. 검수 강화 (일부 완료) | 완료: 재현 테스트의 자기 참조 거부, 부품에 맞지 않는 도구 거부, 정격 판정을 수치 비교로. 남음: reproduce 대조군, 도구 용도 확인 | 자기 참조·오용 0건, 재분석 건당 0.5회 이하 |
| 1-2. 경로·후보 보완 (일부 완료) | 완료: 품질 클레임 경로 정격 점검 (H-L3 재확인, 재분류 없이 결과만 답·8D에 붙임). 남음: 권장 범위를 벗어난 값을 원인 후보에 포함 | H-L2 통과 |
| 2. 도구 확장 | LDO 드롭아웃, 벅 리플 전류·전류 제한 마진, 연산증폭기 4종(슬루율, 오프셋×이득, 동상 범위, 용량성 부하) | 새 도구마다 reproduce·verify 테스트 |
| 3. 평가 확대 | 블라인드 문의 30건 이상, 사람 채점, 3회 반복, 기준선과 비교 | §5 표 |
| 4. 데이터 확장 | 부품 5~10종, 사례 카드 50건 이상 | 카드마다 출처 명시 |
| 5. 비용 관리 | 토큰 기록, 접수·검수에 작은 모델, 검색을 임베딩으로 교체 | 기준선의 5배 이내 |
| 6. 운영 연동 | 승인 채널 연동 (예: Slack), 티켓 시스템 연결 | 실사용 파일럿 |

## 7. 리스크

| 리스크 | 영향 | 대응 |
| --- | --- | --- |
| 검수가 잘못된 통과를 허용 | 근거 없는 초안이 "검증됨"으로 보임 | 1단계에서 검수 규칙 강화, 승인 화면에 테스트 종류 표시 |
| 사용 조건 문제를 품질 불량으로 분류 | "타 버림" 문의가 CPR 경로로 가서 정격 초과 설명이 빠짐 | 품질 클레임 경로에 정격 점검 추가 (완료). 조건 추출 오류와 부품 카드 부족은 위험으로 남음 |
| 새 검수 규칙이 재분석을 늘려 비용 증가 | 구체적 문의에서 재분석 건당 1.58회, 미통과 4건이 토큰의 43% | 고칠 수 없는 지적은 경고로 낮추고 재분석 상한 유지 |
| 평가가 쉬운 문의에 편향 | 실제 성능을 과대평가 | 팀원 블라인드 문의, 실제 E2E 사례를 요약한 문의 추가 |
| 비용·시간 | 건당 토큰이 크고 재분석 횟수가 흔들림 | 재분석 상한 유지, 모델 분리, 토큰 기록 |
| 데이터시트 오독 | 부품 카드의 값이 틀리면 모든 초안이 틀림 | 카드마다 페이지 명시, 두 사람이 교차 확인 |
| 약관 | 자동 수집으로 오해될 여지 | 다운로드는 사람이, 포럼은 요약 카드만 |
| 지원하지 않는 부품군 | 규칙 없는 부품(예: 연산증폭기)은 LLM 추론에만 의존 | 2단계 도구 확장, 지원 범위를 화면에 표시 |

## 8. 팀원에게 정해 달라고 할 것

1. 대상 부품 범위: 이번 3종(LDO, 벅, 연산증폭기)을 유지할지, 5~10종으로 넓힐지
2. 평가용 문의 작성: 각자 **결과를 보지 않고** 문의 몇 건씩 쓸 수 있는지, 사람 채점을 누가 맡을지
3. 우선순위: 1단계(검수 강화)와 2단계(도구 확장) 중 무엇을 먼저 할지
4. 역할 분담(제안): 데이터(부품·사례 카드), 도구(계산·시뮬레이션), 에이전트·프롬프트·검수, 화면·연동, 평가
