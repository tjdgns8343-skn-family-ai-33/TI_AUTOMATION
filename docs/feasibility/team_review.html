Proposal

1. 기획안

고객 문의는 대개 부품 불량이 아니라 회로 설계와 사용 조건 문제입니다. 그래서 문서와 계산으로 풀 수 있고, 결과를 숫자로 확인할 수 있습니다.

풀려는 문제

FAE는 문의마다 데이터시트에서 정격과 조건을 찾고, 손계산이나 시뮬레이션으로 원인을 확인한 뒤 답을 씁니다. 같은 종류의 문의가 반복됩니다.

만들려는 것

근거 페이지와 계산 과정이 붙은 답변 초안. FAE는 처음부터 조사하지 않고 검토하고 승인하는 데 시간을 씁니다.

지키는 원칙

승인 없이는 발송되지 않습니다. 데이터시트는 사람이 내려받고, 포럼은 요약 카드만 씁니다. 실제 고객 정보는 넣지 않습니다.

범위: 세 가지 문의 유형

Architecture

2. 아키텍처

에이전트는 LangGraph로 잇고, 도구는 항상 게이트웨이를 거쳐 부릅니다. 같은 코드가 함수 직접 호출과 MCP 서버 호출 두 방식으로 돕니다.

처리 흐름

테스트의 두 목적 (예: TPS7A20 T-01, 입력 5.5 V → 출력 3.3 V, 0.3 A, 45 °C)

reproduce: 증상이 정말 나오는가

고객 조건으로 계산합니다. 손실 (5.5−3.3)×0.3 = 0.66 W에 θJA 187.1 °C/W를 곱하면 접합 온도는 168.5 °C로 한계 125 °C를 넘습니다. 통과하면 "과열이라는 가설이 맞다"는 뜻입니다.

verify: 해결책이 통하는가

해결책을 적용한 값으로 다시 계산합니다. 입력을 낮춘 안에서 접합 온도가 61.8 °C로 내려가 목표 125 °C 이하입니다. 통과하면 "해결책이 목표를 만족한다"는 뜻입니다.

테스트가 붙는 도구

calc.ldo_thermal_estimate 같은 공식 계산과 spice.run_circuit(ngspice)입니다. 회로 시뮬레이션은 수정 전·후 파형을 겹쳐 화면에 그립니다.

검수 지적과 재분석 규칙

검수 지적원인 분석이 하는 일
reproduce_fail1순위 가설이 증상을 재현하지 못함 → 다음 가설을 1순위로
verify_fail해결책이 목표 미달 → 변경 폭을 키움 (llm은 역산하도록 프롬프트로 안내)
rating_not_addressed정격 초과를 놓침 → 정격 초과 가설을 맨 앞에 추가
no_evidence, test_errorllm에서 지적 내용을 프롬프트로 전달해 다시 작성
알려진 약점: 검수는 "결과가 기대 범위 안인가"만 봅니다. 기대 범위가 의미 있는지(값이 경계와 같지 않은지, 도구가 맞는지)는 보지 않습니다. 정격 초과 판정도 원인 후보에 "정격"이라는 단어가 있는지로 합니다. 3장에서 이 때문에 생긴 문제를 다룹니다.

둘 다 맞혔습니다. 문의가 교과서 수준이라 일반 LLM도 잘 풉니다. 파이프라인의 실제 강점은 정확도보다 근거 페이지와 계산이 붙는 것일 수 있습니다.

파이프라인이 나았던 곳

정답 숫자와 전제 정정입니다. H-T1은 Tj 169.7 °C를 직접 계산했고, H-T2는 기준선이 받아들인 "500 mA까지 된다"를 부품 카드의 300 mA로 바로잡았습니다.

졌던 곳

H-L2 카드에 iout_max 3.0이 있는데 4 A를 못 짚음, H-L3 "타 버림"이라 품질 클레임 경로로 감, H-A2 1순위가 동상 범위 위반. 원인 적중은 오히려 낮았습니다.

검수가 못 잡은 것

측정 문제(H-L1)에 회로 시뮬레이션을 돌린 것, 정보가 없는데 예시 값으로 계산한 것(H-T4). 도구 종류는 맞지만 용도가 틀린 경우입니다.

새 검수는 재분석을 크게 늘렸습니다. 재분석 합 19회(건당 1.58회, 교과서 수준 20건은 3회). 검수 미통과로 끝난 4건(H-T2, H-L2, H-A1, H-A2)이 토큰의 43%(91,505)를 쓰고도 나아지지 않았습니다. 원인은 해결 확인 단계에서 한계값을 그대로 검증값으로 쓴 것(자기 참조)과, 고객이 주지 않은 인덕턴스를 0으로 넣어 계산이 죽은 것(test_error)입니다.
이후 조치 (재측정 전). 자기 참조 지적을 재현 테스트에만 적용하고 해결 확인은 경고로 바꿨습니다. 프롬프트에는 "안 준 값을 0으로 넣지 않는다", "해결 후 값이 한계와 같아지면 여유를 둔다", "핵심 조건이 없으면 예시 값으로 계산하지 않는다"를 추가했습니다. 아직 LLM으로 다시 돌리지 않아 효과는 모릅니다(재측정에 약 20만 토큰 필요).
품질 클레임 경로에 정격 점검을 추가했습니다 (9월 30일). 경로는 바꾸지 않고, 고객이 알려 준 값을 부품 카드 한계와 비교한 결과만 답변·8D·내부 메모에 붙입니다. H-L3를 LLM으로 다시 돌리면(3,512 토큰) 답변 첫 문단에서 "알려 주신 값 기준으로 입력 48 V는 절대 최대 45 V와 권장 최대 40 V를 초과"를 짚고 반품 절차는 유지합니다(정답 숫자 2/2). 진짜 불량 사례(X-01)는 정격 초과를 주장하지 않았습니다. 한계: 접수 단계의 조건 추출이 틀리면 잘못된 비교가 되고(규칙 기반 접수는 "입력 4.5V에서 60V까지"에서 4.5 V를 읽음), 부품 카드가 있는 부품에서만 작동합니다.

이 결과를 읽을 때 주의할 점

  • 문의를 쓴 사람, 시스템을 고친 사람, 채점한 사람이 같습니다. 파이프라인에 유리하게 나왔을 가능성이 있습니다.
  • 실제 고객 문의가 아닙니다. 교과서 수준 18건과 구체적 문의 10건(원인 채점 대상)으로 표본이 작아 결론이 아니라 경향입니다. 구체적 12건도 작성자가 채점했습니다.
  • 새 검수 규칙과 프롬프트 수정의 효과는 아직 LLM으로 재측정하지 않았습니다.
  • 수동 채점은 1회차만 했고 반복 2·3은 자동 판정과 테스트 분석만 했습니다.
  • 연산증폭기는 진단 규칙이 없어서 LLM 추론에만 의존한 결과입니다.
  • 모델은 gpt-5.4-mini 하나만 시험했습니다.
Roadmap

4. 다음 단계

급한 순서대로 나열했습니다. 1번을 하기 전에 평가를 넓히면 잘못된 통과가 섞인 점수가 나옵니다.

순서할 일완료 기준
1검수 강화 (일부 완료): 완료 - 재현 테스트의 자기 참조 거부, 부품에 맞지 않는 도구 거부, 정격 판정을 수치 비교로. 남음 - reproduce 대조군(정상 조건이면 실패해야 통과), 도구 용도 확인(측정 문제에 회로 시뮬레이션), 정보가 없을 때 예시 계산 금지를 코드로 강제자기 참조·오용 0건, 재분석 건당 0.5회 이하
2품질 클레임 경로에서 정격 비교 (완료): "타 버림" 문의도 부품 카드 정격과 먼저 비교해 답변·8D에 붙임 (H-L3 재확인). 남은 것은 조건 추출 오류 방지와 부품 카드 확대H-L3 통과 (확인됨)
3권장 범위를 벗어난 값을 원인 후보에 반드시 포함: 지금은 절대 최대 초과만 강제함 (H-L2의 4 A는 권장 초과라 놓침)H-L2 통과
4도구 추가: LDO 드롭아웃 여유, 벅 인덕터 리플 전류와 전류 제한 마진, 연산증폭기(슬루율, 오프셋×이득, 동상 범위, 용량성 부하 안정성)새 도구마다 reproduce·verify 테스트
5평가 확대: 팀원이 결과를 보지 않고 쓴 문의 30건 이상, 사람 2명 채점, 3회 반복, 기준선과 비교기준선과 같은 원인 적중률, 정답 숫자·전제 정정 비율은 더 높게
6비용 관리: 토큰 기록을 코드에 넣기, 접수·검수에 작은 모델, 재분석 상한 유지기준선의 5배 이내
7인용 검증: 임베딩 검색, 인용한 문장이 근거 조각에 실제 있는지 자동 확인근거 없는 인용 0건

팀원과 정해야 할 것

  • 부품 범위: 이번 3종을 유지할지, 5~10종으로 넓힐지
  • 블라인드 문의: 각자 시스템 결과를 보지 않고 문의 몇 건씩 쓸 수 있는지, 사람 채점을 누가 맡을지
  • 가치 제안: 정확도가 아니라 "근거와 계산 숫자가 붙은 초안 + 사람 승인"으로 갈지
  • 우선순위: 검수 강화(1번), 경로 보완(2·3번), 도구 확장(4번) 중 무엇을 먼저 할지
  • 역할 분담(제안): 데이터(부품·사례 카드), 도구(계산·시뮬레이션), 에이전트·프롬프트·검수, 화면·연동, 평가
