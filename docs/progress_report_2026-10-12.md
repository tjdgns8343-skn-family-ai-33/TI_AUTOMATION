## 1. 한 줄 요약

**반도체 고객 기술 문의를 접수부터 사람 승인까지 처리하는 에이전트(웹 앱 포함)를 만들고, 두 주 동안 "어려운 문의로 재고, 틀린 곳을 코드로 옮기고, 새 문의로 다시 재는" 순환을 세 번 돌렸다.**
반복해서 확인된 결론은 하나다. **코드가 계산해서 넘긴 숫자는 정확하게 답에 실리고, 모델이 스스로 계산해야 하는 숫자는 빠지거나 틀린다.**
그래서 빠진 계산을 설계 점검(`design_check`) 코드로 옮겼다. 이 점검이 새 부품에서도 통한다는 근거는 2건(소프트 스타트, 최소 온타임)이고, **마지막 개선(10/7)의 효과는 아직 LLM으로 재지 않았다.**

## 3. 시스템 구성

```text
브라우저 → frontend (nginx + React) ─ /api ─→ backend (Django) ─→ db (Postgres: 티켓·실행·진행 상태)
                                                   └─ 작업 전달 ─→ redis ─→ worker (Celery: LangGraph 실행)
                                                                                └→ OpenAI (llm 모드만), ngspice, 문서 검색
```

처리 흐름(기술 문의): 접수·분류 → 근거 검색 → **설계 점검(코드)** → 원인 가설 → 계산·시뮬레이션 테스트 → 검수(최대 2회 재분석) → 답변 초안 → **고객 용어 검사** → 사람 승인.
품질 클레임은 정격 점검과 반품 자료 체크로, 배송·기타는 바로 답변 초안으로 간다.

이 두 주에 더한 핵심 부품:

- **설계 점검** (`fae_agent/design_check.py`): LLM 없이 코드가 계산하는 점검을 조사 직후에 둔다. 결과는 분석·답변 프롬프트, 검수, 내부 메모가 같은 값을 쓴다.
  벅(전류 제한, ILIM 골짜기 한계, 잰 리플, 소프트 스타트, 최소 온타임, 최대 듀티), LDO 열, 연산증폭기 오프셋, 충전기(입력 전류 한계, 충전 전력, TS 온도 창), 전 부품 정격(VCC·최저 입력 포함). 상세와 한계는 [architecture.md](architecture.md).
- **원인으로 봐야 할 상태(`COVERAGE`)**: 점검 상태가 원인 가설에 빠지면 검수가 `design_not_addressed`로 되돌리고, mock 분석은 그 가설을 앞에 넣는다.
- **답변 검사** (`fae_agent/reply_check.py`): 파일 이름, "부품 카드" 같은 내부 표현을 고객이 아는 말로 바꾸고 내부 메모에 남긴다.
- **벅 스위칭 시뮬레이션**: 듀티를 찾아 출력을 묶은 뒤 리플과 연속/불연속을 잰다. 계산식과 교차 확인한다.
- **비용 안전장치**: `.env`가 llm 모드여도 CLI는 `--allow-llm` 없이는 거부. LLM 실행은 토큰 예상을 알리고 승인받은 뒤에만 한다.
- **MCP**: 도구를 MCP 서버 4개로 노출해 두었고, 웹 앱과 측정은 함수 직접 호출(`local`)로 돈다.

### 4.2 어려운 문의: TPS62130A D-1 / D-1b (10/1~10/2)

핀 연결 오류(FSW를 12 V에 직결, 절대 최대 7 V) + 인덕터 과소(1 µH, 1.25 MHz → 최대 전류 3.76 A가 전류 제한 최소 3.6 A 초과) + 계산으로 설명되지 않는 리플 70 mV.

| 항목 | 수정 전 (D-1) | 수정 후 (D-1b) |
| --- | --- | --- |
| 핀 절대 최대 초과 | ✓ | ✓ |
| 전류 제한 (3.76 A, 3.6 A, 2.64 A, 2.2 µH) | 방향만 | ✓ |
| 70 mV는 계산 8.7 mV로 설명되지 않음 | ✗ ("맞는다"고 씀) | ✓ |
| 검수 | 통과 | **미통과** (재분석 3회) |
| 토큰 | 46,152 | 48,866 |

- 고친 것은 "계산을 코드로 옮긴 것"(설계 점검 1호)이다. 모델이 똑똑해진 것이 아니다.
- D-1b 검수 미통과: 값 대조의 합격 방향 오류 재발, 내가 만든 "verify는 제한의 0.9배 이하" 규칙이 너무 엄격(데이터시트 권장 2.2 µH가 3번 실패 → "제한 최소값 미만이면 통과"로 고침), 모델이 점검의 "ESR 32 mΩ이어야 설명된다"를 실제 ESR로 넣어 70 mV를 "재현".
- D-1 원문은 제목의 "불량" 때문에 한 번은 품질 클레임으로 분류돼(4,766토큰) D-1b로 제목만 바꿨다. 같은 문의가 두 번 다르게 분류된 것 자체가 발견이다.

### 4.3 어려운 복합 문의 M-1~M-3 (10/2, 88,587토큰, 측정 전에 고치지 않은 문의)

| 문의 | 채점 (원래) | 핵심 |

| M-1 TPS7A20 LDO | ✓5 △1 ✗1 | 열 223 °C, 출력 커패시터 범위 위반, 입력 서지 초과 모두 짚음. 열화상 80 °C ≠ 접합 온도를 설명 안 함 |

- 핵심 원인은 3건 모두 찾았지만 **전 항목 만족은 0건**이었다. 코드가 넘긴 숫자는 정확했고 모델이 계산할 숫자(40 ms, 온타임, 101 mV)는 빠졌다.
- M-3의 최소 온타임 정답은 결과를 본 뒤에 고쳤다(쇼트키 강하 0.4 V를 넣으면 약 136 ns로 최대 130 ns 이상이라 확정 불가). 점수가 올라가는 방향의 수정이라 **원래 채점과 수정 채점을 모두 적었다.**

### 4.5 새 부품 LM5146·BQ25895 (10/7, 138,511토큰)

TI 사이트에서 가장 어렵다고 판단한 두 부품(외부 FET 100 V 벅 컨트롤러, I²C 충전기)을 사용자가 직접 내려받았다. 카드는 표의 열을 쪽 이미지로 확인해 작성했고, 문의 4건의 정답과 채점 기준(7항목)은 **측정 전에 커밋**(`2469149`)했다.
첫 실행은 OpenAI 키 만료(401)로 전부 실패해 토큰 0이었고, 키를 바꾼 뒤 같은 명령으로 다시 돌렸다.

| 항목 | Q-1 LM5146 히컵 | Q-2 LM5146 저입력 | Q-3 BQ25895 입력 전류 | Q-4 BQ25895 TS·감시 타이머 | 합계 |
| --- | --- | --- | --- | --- | --- |
| ✓ / △ / ✗ | 2 / 3 / 2 | 3 / 2 / 2 | 2 / 4 / 1 | 4 / 3 / 0 | **11 / 12 / 5** (28항목) |
| 토큰 | 21,886 | 45,262 | 23,008 | 48,355 | 138,511 |
| 재분석 / 검수 | 0 / 통과 | 3 / 미통과 | 0 / 통과 | 3 / 미통과 | |

- **맞은 것:** 코드 점검이 있던 미끼 2개(소프트 스타트 3.76 ms, 최소 온타임 1.21 µs ≫ 60 ns). 감시 타이머 40 s 후 레지스터 복귀, 4.35 V 셀이 4.2 V에서 끝나는 이유, ILIM 핀과 D+/D− 판별이 입력 전류를 정하는 구조.
- **빠진 것:** 정답 계산(RILIM 133 Ω, 최대 듀티 85~89.5 %, IINMAX 355/470 = 0.755 A, TS 문턱 저항 9.32/8.10 kΩ)은 모두 정성적 설명에 그쳤다.
- **틀린 것:**
  - VCC 14.4 V를 "절대 최대 14 V를 넘는 것은 아니"라고 씀(정격 점검이 입력·전원 전압만 봤음).
  - "인덕터를 키우라"는 권고는 골짜기 한계 방식에서 평균 한계 부하를 오히려 낮춘다(22 µH면 약 7.8 A → 약 7.2 A).
  - 데이터시트의 260 Ω 예시(ILIM 전압 0.4 V를 읽을 때의 모니터 값)를 470 Ω의 근거처럼 잘못 인용.
  - 분석 가설에 IINLIM이 감시 타이머로 초기화된다고 씀(데이터시트 p.31은 IINLIM을 초기화 대상에서 뺌).
  - 쪽 번호 오류 2건(VCC 권장 범위 p.7을 p.1로, 기본값 p.21을 p.1로).
- **비용:** 재분석 3회 두 건이 토큰의 **68 %(93,617)** 를 쓰고 검수 미통과로 끝났다. 원인은 계산 도구가 맞지 않는 부품에서 모델이 `value=30 > 29` 같은 값 대조 테스트를 억지로 만들고 방향 오류·자기 참조가 재발한 것이다. 고객 답변 품질에는 큰 영향이 없었다.
- **주의:** 카드 노트에 히컵 주기, 감시 타이머, D+/D− 표를 내가 먼저 적어 두어 정성 항목 점수가 높게 나왔다. 상세는 [new_devices_2026-10-07.md](new_devices_2026-10-07.md).

### 4.6 약점을 코드로 옮긴 개선 (10/7, 토큰 0, **효과는 아직 재지 않음**)

Q-1~Q-4에서 빠지거나 틀린 것을 점검으로 만들었다: ILIM 골짜기 한계(필요 RILIM, 히컵 주기, "인덕터 키워도 소용없음" 문구), 최대 듀티(필요 듀티 대 1 − tOFF × fsw, 유지 가능한 주파수), 정격 확대(VCC, 최저 입력), 충전기 입력 전류(KILIM/RILIM과 레지스터 중 낮은 값), 충전 전력(효율 90 % 가정), TS 문턱(온도는 NTC 두 점으로 맞춘 곡선의 추정). 새 조건 필드 11개, 접수 규칙, LLM 프롬프트 규칙을 함께 고쳤다.
정답 숫자(6.67/7.79/133 Ω, 89.5/85/90.9 %, 14.4 > 14 V, 0.755/1.31/1.55 A, 9.32/8.10 kΩ)가 단위 테스트에서 점검 결과와 같다. mock 65건 비교: 분류·검수 통과(31건)·재분석 합계(24회) 변화 0.
**이 점검들은 Q-1~Q-4의 약점에서 만들었으므로 그 문의는 더 이상 새 문의가 아니다.**

### 4.7 기존 부품 새 문의 R-1~R-4 (작성·검산 완료, **LLM 측정 승인 대기**)

| | 부품 | 상황 | 정답의 핵심 | 점검 |
| --- | --- | --- | --- | --- |
| R-1 | TPS7A02 | 5 V → 1.8 V, 평균 0.15 A·피크 0.3 A, 45 °C | 접합 132 °C(권장 125 °C 초과, 열 차단 170 °C 아님), 피크가 권장 0.2 A·전류 제한 최소 0.24 A 초과 | LDO 열 있음, 피크는 통제 |
| R-2 | TPS62130A | 1셀 리튬이온 2.9~4.2 V → 3.3 V 2 A | 100 % 듀티 드롭아웃 VIN(min) = 3.3 + 2 × (0.12 + 0.06) = 3.66 V, 최저 입력 2.9 V는 권장 3 V 미만, 전류 제한은 미끼 | 정격 있음, 드롭아웃은 통제 |
| R-3 | LM358 | 단전원 5 V, 이득 1001, 입력 0 V에서 출력 3.4 V | 오프셋 × 이득 3.0/7.0 V(스펙 안), 출력 스윙 3.5 V에서 잘림, GBW로 1 kHz 이득 574배(57 %) | 오프셋 있음, 스윙·GBW는 통제 |
| R-4 | LM5146 | 24 V → 5 V 6 A, 입력이 18.5 V로 처지면 재시작 | UVLO 켜짐 20.6 V·히스테리시스 1.0 V·꺼짐 19.6 V, 필요한 저항 300 kΩ/19.1 kΩ, 전류 제한은 미끼(한계 16 A ≫ 6 A) | ILIM `ok`, UVLO는 통제 |

- 이 문의들을 만들다 발견한 것을 **측정 전에** 고쳤다: 오프셋 문구가 큰 값을 `3e+03 mV`로 찍던 서식, 최대 듀티 폴백이 카드의 전형값을 쓰지 않아 "전형 부품은 유지한다"고 잘못 말하던 것, 카드에 주석으로만 있던 값(TPS7A02 전류 제한 최소·최대, TPS62130A VIN 3 V의 RDS(on), TPS54331 최대 듀티 전형)을 데이터로 올림. 이 카드 값은 정답 일부를 모델에 알려 주는 셈이라 결과 문서에 함께 적는다.
- 새 점검은 LM5146·BQ25895 전용이라 이 4건은 새 점검의 효과보다 **이전 점검이 새 부품에서 통하는지**와 **점검이 없을 때 모델이 카드 공식을 쓰는지(통제)** 를 본다.

## 5. 잘 된 것

- 데이터시트의 숫자를 답에 실어 준다: 절대 최대·권장 한계와 출처(쪽수), 계산값(소모전력, 접합 온도, 대역폭, 소프트 스타트 시간).
- 고객의 틀린 전제를 부품 카드와 점검으로 정정한다("IQ 25 nA면 여유", "SS는 클수록 좋다", "3 V부터 동작하니 3.3 V 유지").
- 계산과 시뮬레이션의 교차 확인이 동작한다(연산증폭기 0.005 % 이내, 벅 리플).
- **측정 방법이 정직하다:** 채점 기준과 정답을 측정 전에 정해 커밋하고, 정답 숫자는 카드와 계산으로 검산하는 테스트로 고정한다. 결과를 본 뒤에 정답을 고쳤을 때는 원래 채점과 함께 적었다.
- 비용 사고를 구조로 막았다(`--allow-llm` 거부, 토큰 예상 후 승인).

## 6. 발견한 문제와 조치

| 문제 | 상태 |
| --- | --- |
| 계산 도구가 맞지 않는 부품에서 값 대조 테스트를 강요해 재분석 3회로 토큰의 68 %를 씀. 값 대조의 합격 방향 오류가 프롬프트·검수 힌트로도 반복됨 (D-1b, Q-2, Q-4) | **미해결.** 코드가 방향을 정하게 하거나 테스트를 요구하지 않는 구조 검토 필요 (큰 변경이라 계획 먼저) |
| 정격 점검이 입력·전원 전압만 봄 (서지 N-L1, VCC Q-1) | VCC·최저 입력은 **수정**. 다른 핀(예: EN 절대 최대)은 카드에 데이터가 없어 미해결 |
| 모델이 계산할 숫자가 빠짐 (소프트 스타트, 최소 온타임, RILIM, 최대 듀티, IINMAX, TS 문턱 등) | 위 항목들을 **점검 코드로 이전**. 효과는 R-1~R-4로 확인 예정 |
| 데이터시트 예시를 다른 조건에 잘못 인용(Q-3), 쪽 번호 오류, 틀린 해결책(Q-1 인덕터) | 미해결(모델 쪽 오류). 점검 문구에 반례를 넣어 일부 막음 |
| 카드의 주석에만 있고 데이터로 없던 값 | 3곳 **수정**. 카드를 쓸 때 주석이 아니라 키로 넣는 것이 원칙 |
| TPS54331 데이터시트의 최대 듀티가 서로 맞지 않음: 표는 최소 90 %·전형 93 %, 설계식은 91 %, 본문은 BOOT 전압이 2.1 V를 넘으면 100 % 듀티 가능 | 점검은 표 값(90 %/93 %)을 쓴다. TPS54331의 최대 듀티 결론은 잠정적이다. 문의로는 아직 검증 안 함 |
| 같은 문의가 두 번 다르게 분류됨(D-1) | 미해결(분류는 문의당 1회만 측정함) |
| 규칙 기반(mock) 접수의 오독(예: "출력이 4.6V로"를 목표 출력으로) | 미해결(LLM 접수는 읽음). mock은 테스트용 |
| OpenAI 키 만료로 측정이 막힘 | 키 교체로 해결. **무료 모델 대체 계획을 제안했고 구현은 보류**(승인 대기) |
| 이전에 발견해 **고친 것:** 테스트 오류 뒤 테스트를 전부 비움, 재현 테스트가 자기 값으로 통과, 부품에 안 맞는 도구, 내부 용어·파일 이름 노출(답변 검사로 0건), 전류 제한 확인 기준(카드의 최소값), PyYAML이 `1.0e6`을 문자열로 읽음(검사 테스트 추가) | 수정 완료, 테스트 추가 |

## 7. 스스로 바로잡은 것

- 승인 없이 LLM 모드가 돌아간 사고(약 10만 토큰, 기록 없음)를 구조(CLI 거부)와 작업 규칙(항상 mock 명시)으로 바꿨다.
- 내가 만든 "verify는 제한의 0.9배" 규칙이 틀렸음을 D-1b에서 확인하고 고쳤다.
- M-3 정답의 최소 온타임이 다이오드 강하 때문에 확정 불가였음을 결과를 본 뒤 알고 고쳤고, 원래 채점과 함께 적었다.
- 설계 점검 확대의 mock 비교에서 `.env`의 ngspice 경로 차이로 생긴 가짜 차이를 발견해 같은 조건으로 다시 비교했다.
- 첫 요약에서 코어 테스트를 "206개 통과"라고 했으나 정확히는 205개 통과, 1개 건너뜀이다.
- 카드 값 오류 3건(LM358 출력 전류, TPS54331 전류 제한과 UVLO 열)은 표를 쪽 이미지로 열어 바로잡았다(9/30).

## 8. 한계

- 문의 작성자, 시스템 조정자, 채점자가 같은 사람이다. 실제 고객 문의가 아니다. 블라인드 문의 30건 이상이 필요하다.
- 어려운 문의는 문의당 **1회** 측정이다(D-1 계열, M-1~M-3, Q-1~Q-4). 같은 문의를 다시 돌리면 달라질 수 있다.
- **일반화의 증거는 약하다.** 점검은 측정에서 드러난 약점으로 만들었고, 새 문의로 재면 그 문의가 다음 개선의 재료가 된다. R-1~R-4도 측정 뒤에는 같은 처지가 된다.
- 카드 노트와 카드 값을 내가 문의보다 먼저 썼기 때문에 정성 항목 점수가 카드 덕을 본다. 정답 일부(Q-3 덮어쓰기 시점, Q-4 NTC 온도, 750 kHz 최대 듀티)는 데이터시트가 직접 주는 값이 아니라 추정이다.
- 도구 없는 LLM 대조군은 가능성 검증 32건에서만 돌렸고, 새 부품·어려운 문의에서는 돌리지 않았다(약 2만 토큰).
- 시뮬레이션은 회로 3개뿐이고 실제 TI IC 모델은 암호화되어 쓸 수 없다. 설계 점검의 가정(RDS(on) 25 °C 값, 효율 90 %, 다이오드 0.4 V, NTC 곡선)은 문서에 적었다.
- 웹 앱은 mock에서 전체 흐름을, llm에서 문의 4건을 확인했다. AWS에서는 돌려 보지 않았다.
- 자동 채점은 믿지 않고 직접 확인했다(숫자 단위 오인정, 근거 목록에 없는 인용 오탐).
