# 개선 로드맵

이 문서는 지금까지 **측정에서 드러난 약점**을 기준으로 다음 개선 방향을 정리한 것이다. 각 항목에 상태를 적었다.
**구현됨**은 코드와 테스트가 있는 것, **계획**은 아직 만들지 않은 것이다. 측정의 한계(표본이 작고 채점자가 작성자)는 [docs/feasibility_report.md](feasibility_report.md)와
[docs/progress_report_2026-09-30.md](progress_report_2026-09-30.md)에 있다.

## 측정으로 확인한 현재 상태

| 측정 | 결과 |
| --- | --- |
| 가능성 검증 32건 (실제 TI 부품 3종) | 원인 적중은 도구 없는 LLM과 비슷하거나 낮았다. 강점은 근거 인용, 계산 숫자, 고객 전제 정정이고 비용은 약 24배였다 |
| 새 부품 12건 | 값 대조(`check_value`)의 합격 방향을 틀려 재분석을 다 쓴 사례가 3건이었고 이 3건이 토큰의 49 %(88,325)를 썼다 → 방향 규칙을 넣었다 (재측정 전) |
| 데이터시트 카드 옮기기 | 손으로 옮긴 카드에서 오류 3건(LM358 전류, TPS54331 전류 제한, UVLO 열)을 쪽 그림 확인으로 잡았다 |
| 어려운 복합 문의 1건 (TPS62130A, D-1) | 46,152 토큰. 핀 절대 최대 초과(FSW 12 V)는 1순위로 맞혔지만 인덕터 최대 전류 대 전류 제한 비교를 놓쳤고, 계산으로 설명되지 않는 리플 70 mV를 "맞는다"고 썼다 |
| 측정 전에 고치지 않은 어려운 문의 3건 (LDO, 연산증폭기, 벅) | 88,587 토큰. 핵심 원인은 3건 모두 찾았지만 모든 항목을 만족한 문의는 0건. 코드가 계산해서 넘긴 숫자는 정확했고, 모델이 스스로 계산해야 하는 숫자(소프트 스타트 시간, 최소 온타임, 오프셋)는 빠졌다. 자세한 채점은 [어려운 문의 측정](hard_cases_2026-10-02.md) |

## 1. 모델

**현재.** 모든 단계가 `gpt-5.4-mini` 하나다. `LLM_MODEL=openai:...` 또는 `anthropic:...`으로 공급자를 바꿀 수 있다. 기술 문의 1건에 1.2만~3.1만 토큰, D-1은 4.6만 토큰이다.

**방향 (계획).**

- 단계별로 모델을 나눈다. 접수 분류와 조건 추출은 작은 모델, 원인 분석과 테스트 설계는 추론이 강한 모델(실패가 몰린 곳), 답변은 중간 모델.
- 후보 모델 3개를 같은 평가셋으로 비교한다 (정확도, 숫자 정확성, 정직성 실패 횟수, 토큰 비용). 모델은 가정이 아니라 측정으로 고른다.
- 평가셋의 일부를 튜닝에 쓰지 않는 검증용으로 떼어 둔다. 지금은 실패 사례를 보고 프롬프트를 고쳤기 때문에 새 부품 측정이 처음으로 일반화를 본 것이다.

## 2. 데이터

**측정된 문제.** PDF 2단 레이아웃이 텍스트 추출에서 섞인다 (TPS62130A p.1 조각이 근거로 인용됨). 표의 최소/전형/최대 열이 텍스트로는 모호하다 (EN 핀 문턱의 열이 반대). 손으로 옮긴 카드에 오류가 있었다.

**방향 (계획).**

| 영역 | 내용 |
| --- | --- |
| 파싱 | 표를 "파라미터, 조건, 최소, 전형, 최대, 단위, 쪽"의 구조화 레코드로 추출하고 자동 검산(최소 ≤ 전형 ≤ 최대, 단위)을 둔다. 애매한 표는 쪽 그림을 비전 모델로 대조한다 |
| 분할 | 고정 길이 조각 대신 절 단위로 나누고 부품, 절, 쪽, 표 번호를 메타데이터로 붙인다 |
| 검색 | 키워드(BM25) + 임베딩 + 부품 번호 필터, 재순위. 검색 자체를 "질문 → 정답 쪽" 세트로 측정한다 (recall@k) |
| 근거 검문 | 인용은 검색된 조각의 쪽 번호만 허용하고 깨진 조각은 근거에서 제외한다 |
| 평가 데이터 | 팀원이 쓴 블라인드 문의 30건 이상을 사람 2명이 채점한다 (작성자와 채점자가 같은 지금의 한계를 없앤다) |

## 3. LangGraph 구성

**현재.** 접수 → 조사 → 분석 → 테스트 → 검수(재분석 최대 2회) → 답변 → 사람 승인. 분석 한 번의 LLM 호출이 가설, 해결책, 테스트 계획을 모두 만든다.

**측정된 문제.** 분석 호출에 규칙이 쌓여 입력이 약 3.8만 토큰이고, 규칙을 일부 지키지 않는다.

| 항목 | 내용 | 상태 |
| --- | --- | --- |
| 결정론적 설계 점검 | LLM 없이 코드가 계산하는 점검을 조사 직후에 둔다. 벅은 인덕터 최대 전류 대 전류 제한, 잰 리플 대 계산을 구현했다 ([docs/architecture.md](architecture.md)의 "설계 점검") | **구현됨** (D-1b로 한 번 재측정) |
| 점검 확대 | 측정에서 빠진 계산을 옮겼다: 소프트 스타트 시간, 최소 온타임(이상적 듀티 대 다이오드 강하 포함, 갈리면 `uncertain`), 오프셋 × 이득, 접합 온도 대 측정한 표면 온도(LDO 열). 새 문의로 재측정은 아직. 남은 것: LDO 드롭아웃, 연산증폭기 대역폭·슬루율의 코드 점검, 모든 핀의 절대 최대 비교, 소프트 스타트 시간 계산 도구(`calc.*`) 새 부품(LM5146, BQ25895) 측정 결과는 [docs/new_devices_2026-10-07.md](new_devices_2026-10-07.md): 28항목 중 ✓ 11, △ 12, ✗ 5로, 점검이 있는 곳은 맞고 없는 계산(ILIM 골짜기, 최대 듀티, 확장 정격, 충전 전류, TS 문턱)은 빠졌다. | **구현됨** (mock 61건 회귀 없음, LLM 재측정 전) |
| 답변 검사 | 고객 답변에 내부 파일 이름·"카드" 같은 내부 용어가 나오지 않는지 답변 뒤에 코드로 검사하고 고객이 아는 말로 바꾼다 (프롬프트로 금지해도 M-3에서 `tps54331.pdf`가 노출됨) | **구현됨** (mock 답변 29건의 내부 표현이 0건, LLM 재측정 전) |
| 병렬 계산 | LangGraph `Send`로 점검을 병렬 실행하고 분석을 "가설 생성"과 "테스트 설계"로 나눈다 | 계획 |
| 비평 노드 | 답변의 모든 숫자가 도구 출력에서 나왔는지(출처 추적), 고객 측정값과 계산의 불일치를 점검한다 | 일부 **구현됨** (불일치) / 출처 추적은 계획 |
| 질문 분기 | 정보가 부족하면 추측하지 않고 고객 질문 단계에서 멈춘다 | 계획 |
| 관측성 | 노드별 토큰, 지연, 재분석 사유를 기록한다 (지금은 재분석마다 검수 지적이 남지 않아 체크포인트 이력으로 역추적한다) | 계획 |

## 4. 시스템 프롬프트

**측정된 문제.** 실패 사례마다 규칙을 덧붙이는 방식이라 길어졌고, 일부 규칙(ESR을 0으로 넣지 않기, 동기 벅의 다이오드 강하)은 따르지 않았다.
이 두 규칙은 프롬프트에 더해 검수 경고로도 걸리게 했다 (**구현됨**, 재측정 전). 프롬프트에 적는 것만으로는 지켜지지 않았기 때문이다.

**방향 (계획).**

- 정책(정직성, 인용, 추측 금지), 절차(단계), 도메인 지식을 분리한다. 공식과 한계값은 프롬프트가 아니라 도구와 부품 카드에 둔다.
- 프롬프트가 아니라 스키마로 강제한다 (`expect`의 지표 이름을 도구 목록의 값으로 제한, 인자 0은 카드가 허용할 때만).
- 부품 종류별 모듈(벅, LDO, 연산증폭기)을 동적으로 불러 길이를 줄인다.
- 규칙 하나마다 실패 사례, 단위 테스트, 재측정 결과가 짝을 이루게 한다. 일부는 이미 그렇다 (프롬프트 예시 숫자를 계산으로 검증하는 테스트, 값 대조 방향 테스트).

## 5. 회사 내부 데이터에 접근할 수 있다면

회사 내부 시스템은 이 프로젝트가 알 수 없다. 아래는 이 프로젝트에서 겪은 한계에 대응하는 **확인해 볼 방향**이다.

| 지금 한계 | 접근 권한이 있으면 |
| --- | --- |
| PDF를 읽어 카드를 만들다 오류 3건 | 제품 파라미터의 구조화된 원본을 바로 사용 → 옮겨 적는 오류와 파싱 비용 제거 |
| 시뮬레이션이 이상적 스위치에 가정값 (평가 보드 측정과 비교 못 함) | 내부 SPICE 모델과 평가 보드 측정 데이터로 템플릿을 검증하고 오차를 정량화 |
| 평가 문의를 직접 작성 (작성자 = 채점자) | 익명화한 실제 지원 이력으로 평가셋을 만들고 담당 엔지니어의 답변과 일치도를 측정 |
| 사람 승인 단계의 결과가 학습에 안 쓰임 | 초안을 얼마나 고쳤는지(수정 거리)와 반려 사유를 개선 신호로 사용 |
| 외부 모델 사용 | 고객 기밀과 수출 통제 때문에 내부 승인된 모델 엔드포인트를 쓰는 구성을 고려 |

성과 지표는 첫 응답 시간, 담당자 소요 시간, 담당자 답변과의 일치도, 건당 비용이다. 고객에게 나가는 답변은 항상 사람 승인을 거친다.
